# 后端后续任务清单

本文档记录当前项目管理系统后端后续需要完成的修改任务。当前后端为 Node.js 原生 HTTP 服务 + 数据库存储，已具备基础 CRUD、状态同步、库存汇总、项目详情聚合、系统仪表盘统计和基础校验。本地默认 SQLite，生产部署推荐 PostgreSQL。

## 目标

后端后续建设目标是从“可演示的数据服务”升级为“可多人使用、可长期维护、数据可靠的内部业务系统后端”。

核心方向：

- 数据可靠：从 JSON 文件迁移到数据库，保证并发写入和数据完整性。
- 接口清晰：前端逐步从整包 `PUT /api/state` 切换到对象级 CRUD。
- 业务准确：采购、入库、出库、库存、项目进度统计口径统一由后端计算。
- 可维护：增加配置、错误处理、测试、部署和数据备份方案。

## P0：后端基础稳定性

优先级最高，建议下一阶段先做。

| 状态 | 任务 | 说明 | 验收标准 |
|---|---|---|---|
| 已完成 | 增加后端自动测试 | 覆盖 CRUD、级联删除、库存校验、入库数量校验、系统仪表盘接口 | `npm test` 可一键运行，关键接口测试通过 |
| 已完成 | 统一错误响应格式 | 错误返回 `error.code`、`error.message`，可选 `details` | 前端能根据错误码做明确提示 |
| 已完成 | 增加请求参数校验 | 对 `limit`、`sort`、日期、状态、数字等参数做明确校验 | 非法参数返回 `400`，不产生脏数据 |
| 已完成 | 完善 `PUT /api/state` 风险控制 | 使用 `ALLOW_STATE_WRITE=false` 可关闭整包覆盖保存 | 生产使用时可关闭完整覆盖接口 |
| 已完成 | 增加数据备份机制 | 写入前自动备份业务数据快照，可配置备份目录和保留数量 | 可从最近备份恢复业务数据 |

## P1：数据库化

当前已支持本地 SQLite 和生产 PostgreSQL。未配置 `DATABASE_URL` 时使用 SQLite，便于开发和演示；配置 `DATABASE_URL` 后自动切换到 PostgreSQL，适合多人部署和长期运行。

| 状态 | 任务 | 说明 | 验收标准 |
|---|---|---|---|
| 已完成 | 确定数据库选型 | 本地默认 SQLite；生产部署选择 PostgreSQL | 形成明确选型说明 |
| 已完成 | 实现数据库 schema | SQLite 和 PostgreSQL 均按业务表落库 | 项目、任务、BOM、采购、采购明细、入库、出库、字典表全部建表 |
| 已完成 | 编写迁移脚本 | 首次启动从 `backend/data/db.json` 或 `backend/data/seed.json` 导入数据库 | 现有演示数据可完整迁移 |
| 已完成 | 抽象数据访问层 | 后端业务通过 `backend/storage.js` 自动选择 SQLite 或 PostgreSQL | CRUD、查询、统计走统一存储入口 |
| 已完成 | 增加事务处理 | 写入完整业务状态时使用数据库事务保护 | 任一步失败时数据不半写入 |

## P2：接口拆分和业务服务化

逐步减少前端整包读写，改为细粒度接口。

| 状态 | 任务 | 说明 | 验收标准 |
|---|---|---|---|
| 已完成 | 前端切换为对象级 CRUD | 新增/编辑/删除项目、任务、BOM、采购、出入库时调用对应接口；系统设置调用 `/api/settings` | 不再依赖每次保存完整 `state` |
| 未开始 | 项目详情接口继续增强 | `/api/projects/{id}/detail` 增加统计、风险、近期采购、库存摘要 | 项目详情页无需前端二次拼装大量数据 |
| 未开始 | 采购管理专用接口 | 增加采购列表、采购详情、采购明细聚合接口 | 采购页能直接分页、筛选、查看详情 |
| 未开始 | 出入库管理专用接口 | 增加入库视图、出库视图、库存流水接口 | 出入库页不再由前端自行拼接采购/BOM/库存 |
| 未开始 | BOM 生成采购接口 | 后端提供“从 BOM 项生成采购明细/采购记录”的业务接口 | 前端只提交 BOM 项和采购基本信息 |

## P3：统计口径后端统一

目前首页统计前端仍有一套计算逻辑，后端也新增了 `/api/dashboard`。后续要统一口径。

| 任务 | 说明 | 验收标准 |
|---|---|---|
| 首页完全使用 `/api/dashboard` | 前端首页不再自行计算系统指标 | 首页指标与后端返回完全一致 |
| 项目概览使用 `/api/projects/{id}/dashboard` | 项目内仪表盘指标由后端提供 | 项目详情页统计口径统一 |
| 明确风险规则 | 如任务逾期、采购逾期、交付临近、采购异常等 | 形成可配置或可维护的风险规则 |
| 明确库存口径 | 已入库、已出库、当前库存、未入库、部分入库/出库 | 后端、前端、文档口径一致 |
| 增加统计缓存或优化 | 数据量大后避免每次全量遍历 | 常用统计接口响应稳定 |

## P4：系统配置和字典管理

当前系统设置为简单数组，后续需要更完整的数据结构。

| 任务 | 说明 | 验收标准 |
|---|---|---|
| 字典项改为对象结构 | 增加 `id`、`type`、`value`、`sortOrder`、`enabled` | 可停用、排序、避免重复 |
| 字典项引用检查 | 删除状态、供应商等选项前检查是否被业务数据使用 | 被引用时禁止删除或要求替换 |
| 增加默认值策略 | 新建项目/任务/采购时后端可提供默认状态 | 前端减少硬编码 |
| 系统配置导入导出 | 方便备份和初始化 | 能导出/导入系统字典配置 |

## P5：文件与导入能力

虽然一期不要求 Excel 导入，但后续 BOM 和采购记录大概率需要批量处理。

| 任务 | 说明 | 验收标准 |
|---|---|---|
| BOM 批量导入接口 | 支持上传 Excel/CSV，映射到 BOM 项字段 | 可预览、确认、导入 |
| 采购明细批量导入接口 | 支持采购部门表格导入采购记录和采购明细 | 能识别采购记录和明细行关系 |
| 导入校验报告 | 返回缺字段、重复项、非法数量等问题 | 导入前可修正问题 |
| 文件存储策略 | 明确上传文件保存位置和命名规则 | 来源文件可追溯 |

## P6：账号、权限、日志

一期暂不做，但后续多人使用时必须补。

| 任务 | 说明 | 验收标准 |
|---|---|---|
| 登录认证 | 可先做简单账号密码，后续可接企业微信/LDAP | 非登录用户不能访问系统 |
| 角色权限 | 项目负责人、研发、采购、仓库/物料人员等 | 不同角色只能操作对应模块 |
| 操作日志 | 记录增删改、出入库、导入、状态变更 | 可按对象查看历史 |
| 数据版本/审计 | 重要字段变更前后值可追溯 | 可定位谁在什么时间改了什么 |

## P7：部署和运维

从本地开发走向公司内网部署需要补齐。

| 任务 | 说明 | 验收标准 |
|---|---|---|
| 环境配置 | `PORT`、数据库连接、备份目录、日志目录等使用环境变量 | 不同环境无需改代码 |
| 生产启动方式 | 使用 PM2/systemd/Docker 等方式守护进程 | 服务异常后能自动恢复 |
| 日志文件 | 记录访问日志、错误日志、关键业务日志 | 可定位线上问题 |
| 健康检查接口 | 如 `/api/health` | 部署平台可检测服务状态 |
| 备份恢复流程 | 数据库和上传文件定期备份 | 有明确恢复步骤 |

## 建议实施顺序

1. 先补自动测试和错误格式，避免后续改动引入回归。
2. 再做数据库迁移，解决文件存储和并发问题。
3. 然后把前端保存逻辑从 `PUT /api/state` 切到对象级 CRUD。
4. 再把首页、项目概览、采购、出入库的统计和聚合接口统一到后端。
5. 最后补权限、日志、导入、部署能力。

## 当前不建议立即做的事项

- 不建议马上接 IM 系统：当前核心问题是业务数据结构和流程闭环。
- 不建议马上做复杂审批流：用户已明确系统只记录，不走审批。
- 不建议马上做精细权限：一期由项目负责人统一维护，权限可等多人使用前再做。
- 不建议过早引入复杂微服务架构：当前单体后端更容易维护和迭代。
